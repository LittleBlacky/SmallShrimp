# Task Flow Retrospective

## 目标

把一次已完成的任务流程复盘成可复用方法论，帮助下次在相似场景中更快识别目标、复用步骤、验证结果并避免重复踩坑。

## 使用前收集

优先从对话、工具记录、文件变更和用户反馈中提取信息；只在关键缺口会影响复盘质量时追问。

需要明确：

- 原始目标：用户当时要解决什么问题，成功标准是什么。
- 上下文：输入材料、限制条件、已有资源、风险和依赖。
- 实际过程：关键决策、工具使用、分支尝试、失败与修正。
- 最终结果：交付物、验证结果、用户反馈和遗留问题。

## 复盘步骤

1. **还原任务目标**：用一句话描述任务目的，并列出显性和隐性成功标准。
2. **梳理上下文**：记录触发背景、输入、约束、相关环境和必须保留的假设。
3. **分解执行流程**：按真实发生顺序列出步骤，标注关键判断点、工具或资料来源。
4. **提炼验证方式**：说明如何确认结果正确，包括检查点、测试提示、人工评审标准或可观察证据。
5. **沉淀经验**：区分可复用做法、失败模式、风险提醒和可提前准备的模板。
6. **定义下次触发条件**：写清哪些用户表达、任务形态或上下文信号应触发这套方法。
7. **压缩成方法论**：把一次性细节抽象成可迁移步骤，避免把偶然信息写成固定规则。

## 输出模板

```markdown
# [任务/方法论名称] 复盘

## 1. 目标
- 任务目标：
- 成功标准：

## 2. 上下文
- 输入与资源：
- 约束与风险：
- 关键假设：

## 3. 执行步骤
1. ...
2. ...
3. ...

## 4. 验证方式
- 检查点：
- 通过标准：
- 失败时回退方案：

## 5. 经验沉淀
- 可复用做法：
- 常见坑：
- 下次可提前准备：

## 6. 下次触发条件
- 触发表达：
- 适用场景：
- 不适用场景：
```

## 质量标准

- 保持事实和推断分离；没有证据的内容标为“推测”或向用户确认。
- 优先沉淀可迁移流程，而不是复述流水账。
- 每个执行步骤都应能回答“为什么这一步必要”和“怎么知道做对了”。
- 下次触发条件要具体到用户表达或任务信号，例如“把这次流程沉淀一下”“复盘刚才的处理过程”“整理成 SOP”。
- 如任务涉及敏感信息，复盘时保留方法，去除不必要的账号、密钥、个人信息和内部细节。

## 测试提示

- “把刚才修复部署失败的过程复盘成一个以后可复用的排障 SOP。”
- “我们刚完成了一次竞品资料整理，请沉淀成下次做资料研究时可复用的方法论。”
- “复盘这次创建 skill 的流程，输出目标、上下文、步骤、验证方式、经验和下次触发条件。”

## 验证指引

检查输出是否同时覆盖目标、上下文、执行步骤、验证方式、经验沉淀和下次触发条件；是否把一次性细节抽象成可复用规则；是否明确哪些场景不该套用该方法。
