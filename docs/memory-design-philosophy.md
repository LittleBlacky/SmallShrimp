# 记忆层设计哲学

> 从记忆的本质出发，推导出 SmallShrimp 的记忆架构。
> 这不是一份 API 文档，而是一份设计思想的演进记录。

---

## 一、记忆的本质

### 1.1 记忆的定义

**记忆 = 过去的信息，在未来被需要时能找回来。**

这个定义拆开来看，有几个关键点：

| 要素 | 含义 | 做不到会怎样 |
|------|------|-------------|
| **过去的信息** | 不是当下的输入，是已经发生过的事情 | — |
| **在未来被需要** | 存它是为了以后用，不是存着好看 | 存了一堆没用的东西 |
| **能找回来** | 需要的时候能搜到，而不是石沉大海 | 存了等于没存 |

由这个定义，推导出记忆系统必须回答的五个问题：

```
① 什么值得存？      → 鉴别（值得跨会话保留的信息才写）
② 存成什么格式？    → 存储（什么格式查询最快）
③ 怎么找回来？      → 检索（从存储中找到相关内容）
④ 怎么确保找对了？  → 排序（把最相关的排前面）
⑤ 不需要的怎么办？  → 遗忘（让过期的信息淡出）
```

这五个问题的答案，就是整个记忆架构。

## 二、记忆的来源

### 2.1 记忆从哪里来

```
对话过程
    │
    ├── 用户明确说"记住"          ──→  显式记忆
    ├── 用户纠正了 Agent 的错误   ──→  修正记忆
    ├── Agent 执行任务失败了      ──→  教训记忆
    ├── Agent 从对话中提取出事实  ──→  萃取记忆
    └── 用户反复提到同一件事      ──→  强化记忆
```

### 2.2 什么才值得存

不是所有信息都值得进入长期记忆。判断标准就一条：

**这条信息在下一次会话中还会被用到吗？**

```
值得存:
  "用户对花生过敏"       → 下次点餐还要用
  "预算不超过 500"       → 每轮都要注入
  "用户是后端开发"       → 长期画像
  "之前递归调用栈溢出了"  → 下次写代码要记住

不值得存:
  "帮我写一段排序算法"    → 一次性请求
  "今天天气怎么样"        → 过期无关
  "好的，明白了"          → 寒暄
  "帮我把灯关了"         → 一次性操作
```

但这里有一个矛盾：**判断一条信息未来会不会被用到，本身就需要对未来的预测能力**。我们没有预测能力，所以只能退而求其次——用规则和 LLM 来近似判断。

当前的做法：

```python
# 一定会存（规则触发）
correction_detected  → 写 profile
failure_detected     → 写 reflections

# 可能会存（LLM 判断）
post_turn_extraction → LLM 判断"这段对话有什么值得记住的"
```

这就是为什么当前的 `post-turn` 提取只能作为补充，不能作为主通道——它依赖 LLM 的判断，而 LLM 的判断是不稳定且昂贵的。真正可靠的，还是 `correction` 和 `failure` 这种确定性信号。

## 三、记忆的存储

### 3.1 存储选择的演进

确定了要存什么之后，下一个问题是：存成什么格式？

```
一段原始文本: "用户对花生过敏，在腾讯工作，正在学 Python"

如果直接存原文:
  存: "用户对花生过敏，在腾讯工作，正在学 Python"
  搜: 搜"过敏" → 命中，但搜"腾讯"也返回整段
  问题: 和"用户在北京工作"混在一起，分不清哪个是哪个

如果按实体存:
  存:
    (用户) —[过敏]→ (花生)
    (用户) —[工作于]→ (腾讯)
    (用户) —[学习]→ (Python)
  搜: 搜"过敏" → 直接沿边找到花生
  搜: "腾讯和 Python 什么关系" → 图遍历一次找到
```

**不是所有信息都需要图结构**：

```
适合文本的（FTS5）:
  "Python 是动态类型语言"
  → 这是一个独立知识点，不需要和其他东西关联
  → 搜"Python"能搜到就行

适合图的（Neo4j/SQLiteGraph）:
  (用户) —[过敏]→ (花生)
  → 价值在于"用户"和"花生"之间的关系
  → 搜"过敏"时不仅要找到"花生"，还要找到和"花生"同类的东西
```

### 3.2 存储的逐层递进

基于上述分析，存储应该分两层，每层有不同的格式和引擎：

```
第一层：文本存储（BuiltinProvider，SQLite + FTS5）
  存的内容: profile / constraints / facts / reflections / sessions
  特点: 独立知识点，无复杂关联
  检索: FTS5 关键词 + 可选向量语义
  门槛: 零依赖

第二层：图谱存储（GraphProvider，SQLite 或 Neo4j）
  存的内容: entities / relations / events / insights
  特点: 数据之间有明确的关系
  检索: 图遍历 + 向量 + 全文
  门槛: 默认 SQLite（零依赖），进阶 Neo4j（需 Docker）
```

两层的关系不是互斥的，而是互补的：**profile 存"用户是后端开发"，entity 存(用户)—[职业]→(后端开发)**，两份数据但同一件事。profile 用于每轮快速注入，entity 用于关系查询。

## 四、记忆的检索

### 4.1 检索的本质

检索的本质不是"搜到"，而是**从存储中找到与当前上下文最相关的信息**。

```
用户说: "帮我推荐一个类似上次的框架"
          ↓
需要找到: 上次用了什么框架 + 它的特点 + 同类替代
          ↓
存储里有的信息:
  · profile: "用户用过 Flask"        ← FTS5 搜"框架"命中
  · entity: (Flask)—[是]→(微框架)   ← 图遍历找到关联
  · facts: "Django 比 Flask 重"     ← 向量搜"类似"命中
```

### 4.2 检索的层次

```
用户输入
    │
    ▼
第一层：关键词（FTS5，必有）
  命中包含关键词的记录
  速度: ~10ms
  依赖: 无

    │ （如果配置了 embedding）↓
    ▼
第二层：语义（向量，可选）
  找语义近似的记录
  速度: ~20ms
  依赖: 本地模型或 API key

    │ （如果开启了图谱）↓
    ▼
第三层：关系（图谱，可选）
  找实体关联
  速度: ~10-50ms
  依赖: SQLite（无）或 Neo4j（Docker）
```

### 4.3 多路融合排序

当多个引擎都返回结果时，需要融合排序：

```python
def fusion_sort(results):
    # 1. 按 record_id 去重（同一条记录不会重复返回）
    # 2. 每条记录综合评分
    for r in results:
        r.score = (
            r.fts_score × 0.30 +      # 关键词匹配度
            r.vec_score × 0.35 +      # 语义相似度
            r.importance × 0.10 +     # 记忆本身的重要度
            r.popularity × 0.10 +     # 检索热度
            r.recency × 0.10 +        # 时效性
            r.layer_bonus × 0.05      # 层优先级
        )
    # 3. 返回 top-5
    return sorted(results, key=lambda r: r.score, reverse=True)[:5]
```

### 4.4 什么算"有效"的记忆

融合排序前有一条硬线：**低于这条线的记忆根本不进入排序**。

```
有效记忆 = 满足任意一条:
  · FTS5 命中（关键词有匹配）
  · 向量余弦 ≥ 0.6（语义够接近）
  · 图谱实体直接关联（有关系边）

无效记忆:
  · 向量余弦 < 0.4（语义太远）
  · 时间衰减 < 0.1（太久远）
  · 图谱弱关联（connect_strength = weak）
```

这条线确保 LLM 看到的候选至少和当前问题沾边，不会拿完全无关的东西去浪费上下文。

## 五、记忆的筛选与遗忘

### 5.1 筛选

写入记忆前的最后一道关：**这条记忆值得保留吗？**

```
检查清单:
  □ 是跨会话可复用的信息吗？
  □ 是事实性信息（不是临时状态）？
  □ 是一次性操作/闲聊吗？（→ 拒绝写入）
  □ 和已有记忆矛盾吗？（→ 标记待确认）
```

### 5.2 遗忘

记忆不是存进去就不管的。需要遗忘机制：

```
时间推演:
  第一天: 用户说"我在北京工作"
          → 写入 profile，importance=7
  第十天: 用户说"我搬到上海了"
          → 写入新 profile
          → Dreaming 检测到"北京"和"上海"是同一属性变更
          → 旧记忆标记为"过期"，新记忆设为当前有效
  第三十天: 用户换了三次工作
            → 早期的工作信息 access_count 一直为 0
            → 自动降权，不再出现在默认检索结果中
  第九十天: "在北京工作" 从未被检索过
            → LRU 淘汰
```

遗忘策略：

| 策略 | 触发条件 | 效果 |
|------|---------|------|
| 时间衰减 | 超过 30 天未访问 | 排序权重降低 |
| 热度淘汰 | 条数超限时 | 最低 access_count 的先淘汰 |
| 对立检测 | 检测到矛盾记忆 | 标记待确认，不自动删除 |
| 置信度衰减 | 长时间未验证 | 从 1.0 逐步降到 0.5 以下不出现 |

## 六、演进过程

### Phase 0：只有文本

```
记忆 = 存文本 → FTS5 搜文本
够用场景: 个人笔记、简单问答
瓶颈: 搜不准、不会遗忘
```

### Phase 1：分级 + 约束隔离（已完成）

```
记忆 = 文本 + 分层（profile/facts/reflections/constraints/sessions）
     + 约束不参与压缩（ContextGuard）
     + 高频记忆自动浮出（access_count）
     + 跨层不误合并（层组去重）
```

### Phase 2：向量语义增强（代码已有，可选开）

```
记忆 = 文本 + 分层 + 约束隔离
     + 可选向量语义（FTS5 + sqlite-vec）
     + 可选 API embedding（OpenAI 兼容）
```

### Phase 3：图谱关系（设计中）

```
记忆 = 文本 + 分层 + 约束隔离 + 向量
     + 可选实体关系图（SQLite 或 Neo4j）
     + LLM 萃取管线（陈述 → 三元组）
```

### Phase 4：遗忘与整合（未来）

```
记忆 = 以上全部
     + 置信度衰减
     + 矛盾自动检测
     + 层级提升（short → long）
     + 定期整合（Dreaming 强化）
```

## 七、设计原则总结

```
① 记忆的本质是"过去的信息在未来被需要时能找回来"
   → 所有设计围绕"存什么、怎么存、怎么找"展开

② 不是所有信息都值得存
   → 跨会话可复用是唯一标准

③ 不是所有信息都要进图
   → 有关系的进图，没关系的进文本

④ 检索不是越全越好
   → 宁少勿多，一条不相关的记忆比一条缺失更糟糕

⑤ 遗忘和存储同样重要
   → 不淘汰的信息最终都会变成噪声

⑥ 能力渐进增强
   → 用户从零依赖起步，需要时才叠加能力
   → 每一步升级不影响已有功能
```
